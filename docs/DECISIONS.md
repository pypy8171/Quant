# 결정 기록

무엇을 왜 바꿨는지 남긴다. 코드와 git 히스토리로 알 수 있는 "무엇을"이 아니라, 거기 안 남는
**"왜 그 대안이 아니라 이것인가"**를 적는 것이 목적이다.

## 기록 원칙

- 판단 기준은 **어느 쪽이 나은가**다. "기존 정의가 바뀐다" "고칠 게 많다"는 비용 항목이지 기각 사유가 아니다.
  기각은 "더 나쁘다"는 근거가 있을 때만 한다.
- 채택안뿐 아니라 **버린 대안과 버린 이유**를 같이 적는다. 나중에 같은 논의를 반복하지 않기 위해서다.
- 나중에 틀린 것으로 드러나면 항목을 지우지 말고 `상태`를 갱신하고 후속 항목에서 뒤집는다.
- 증거가 없으면 없다고 적는다. "엣지가 있다"와 "측정한 적이 없다"를 구분한다.

## 양식

```
### D-NNN 제목 (YYYY-MM-DD)
**상태**: 채택 / 철회 / 진행 중 / 보류
**결정**: 한두 문장.
**배경**: 무엇이 문제였는지. 가능하면 측정값.
**대안 비교**: 검토한 안과 각각을 택하지 않은 이유.
**근거**: 왜 이게 낫다고 보는지.
**남은 위험**: 이 결정이 해결하지 못한 것.
```

### D-003 DevScale 개장 구간 기준점 — 일봉 기준 매매 후 3분봉 전환 (2026-09-07)
**상태**: 진행 중 (설계 회의 결과 대기)

**결정**: 09:00부터 매매가 되도록 개장 구간의 기준선을 3분봉 SMA20이 아닌 **일봉 기준값**으로 두고,
3분봉이 일정 수 쌓이면 3분봉 체계로 넘긴다. 전환 임계는 고정값으로 박지 않는다.

**배경**: 3분봉 SMA20은 20봉×3분 = 60분 워밍업이 필요해 09:57까지 주문이 나가지 않는다.
로그 8거래일 전부에서 09시대 분할 매수 재구성이 09:57 한 분에만 찍혔다(41건). 결정론적 장벽이다.

**PIT 풀 재검증 — 기저 자체가 음수다**: 위 표의 종목 풀은 "오늘 기준 거래대금 상위 500"이라
생존·선정 편향이 있었다. 상폐 포함 3,004종목·434만 종목·일로 풀을 다시 만들고, 날짜별 거래대금
20일 평균 순위로 그날의 상위 500을 뽑아 같은 측정을 반복했다(`bars_all_pit.parquet`).

존재했던 전체 집합에서는 손실이다.

**대안 비교**

| 안 | 판정 |
|---|---|
| `sma_period` 20→5 축소 | 기각. 신봉 1개당 기여가 4배 커져 데드밴드를 매 봉 넘긴다. 취소–재주문 처닝이 재현된다(08-10 458210 접수 196·취소 183, 09-03 거부 87건이 같은 실패 모드) |

| 전일 분봉으로 SMA 시딩 | 기각. 데이터는 확보 가능하나(아래 D-004) 기준점이 전일 종가대에 고정된다. 갭 3%면 매도 rung이 전부 현재가 아래로 깔려 지정가 매도가 투매가 된다. 봉당 갭/20씩만 수렴 |
| 당일 시가로 패딩한 합성 SMA20 | 기각. 갭은 흡수되지만 실재하지 않는 통계량을 만들어 쓴다. 아래 채택안이 실재 확정값을 쓰므로 이걸 택할 이유가 없다 |
| **일봉 기준점 → 3분봉 전환** | **채택 후보.** 09:00 시점에 일봉SMA20은 이미 확정돼 있고 당일 일봉(시가·고저·현재가)은 실시간이다. 합성이 필요 없다 |

**근거**: 없는 값을 만들어 쓰는 대신 이미 있는 값을 쓴다. 워밍업이 원리적으로 사라진다.
개장 구간과 장중 구간이 다른 체계라는 것을 숨기지 않고 분리해 정의하므로, 나중에 각각을 따로 측정할 수 있다.

**남은 위험**
- 일봉 기준점에 `dev_sell_pct=1.5`를 그대로 쓰면 안 된다. 존 게이트가 일봉SMA20 대비 −8%~+5%를 허용하므로,
  현재가가 기준점 위 3%인 정상 상태에서 매도 rung이 현재가 아래로 깔린다. 개장용 밴드는 별도 파라미터가 필요하다.
- 일봉 스냅샷 자체가 오염돼 있다(D-005). 새 안은 이 값을 분할 매수 가격 결정에 직접 쓰므로 영향이 커진다.
- 개장 구간 수익성은 이 저장소에서 측정된 적이 없다. 스터디 11개가 전부 일봉이고 장중 백테스트 하네스가 없다.
  현 단계에서 주장 가능한 것은 "엣지를 추가한다"가 아니라 **"미정의 구간을 정의해 계측 가능하게 만든다"**까지다.
- 모의계좌는 당일 매수분 당일 매도가 안 돼 익절 레그가 체결되지 않는다. 왕복 손익은 모의로 측정할 수 없다.

### D-004 전일 분봉 API 배선 — 라이브 미투입, 백테스트 전용 (2026-09-07)
**상태**: 진행 중

**결정**: 과거 날짜 분봉을 받는 TR `FHKST03010230`(`inquire-time-dailychartprice`)을 배선하고
디스크에 캐시한다. 다만 **라이브 신호에는 넣지 않고** 오프라인 백테스트 입력으로만 쓴다.

**배경**: 현행 `get_minute_ohlcv`는 당일에 갇혀 있다. `KisClient.cpp:813`의 `if (prev < 90000) break;`이
당일 09:00 이전으로 못 넘어가게 막고, TR `FHKST03010200`에는 날짜 인자 자체가 없다.
그래서 종목 분봉 히스토리가 저장소에 0건이고, 장중 전략을 오프라인에서 검증할 방법이 없었다.

**실측 확인**: 날짜 인자를 받는 다른 TR로 1콜에 1분봉 120개(130분)를 받는다. 1년 전 날짜도 응답하고,
모의 도메인에서도 동작한다. 현행 3분봉 60분치가 3콜인데 이 TR은 1콜이면 된다.

**대안 비교**: 라이브 SMA 시딩에 바로 쓰는 안은 D-003에서 기각했다(stale anchor).
데이터 확보와 라이브 투입을 분리해, 확보는 지금 하고 투입 여부는 백테스트 결과로 정한다.

**근거**: 장중 전략의 엣지 유무를 판정할 유일한 경로다. 지금까지 "3분봉 오프라인 백테스트 불가"로
닫아 뒀던 판단은 이 TR 기준으로 갱신된다. 라이브에 안 넣으므로 이 단계의 리스크는 0이다.

**남은 위험**: 실측은 005930 한 종목·몇 개 날짜뿐이다. 유니버스 40종목 × 6개월 백필을 한 번 돌려
결측률을 봐야 커버리지가 확정된다. 15:30 종가 단일가 봉을 포함할지도 정해야 한다.

**호출 비용**: 전일 분봉은 마감 후 불변이라 장 마감 배치로 캐시하면 09:00에 추가 조회가 없다.
09:00 전후는 이미 REST 버킷이 포화라(09-07 HTTP 500 분포 08:55=31, 09:00=32, 09:26=32, 09:50=32)
여기에 조회를 얹는 설계는 피해야 한다.

### D-005 일봉 스냅샷 look-ahead — 당일 봉 절단 (2026-09-07)
**상태**: 채택 (구현·빌드 완료, 라이브 미검증)

**결정**: `get_daily_ohlcv`가 응답에서 오늘(KST) 날짜 행을 버린다.
시그니처에 `include_today=false` 기본값을 두고, 캐시 키에 그 값을 넣는다.
당일 봉이 실제로 필요한 곳은 파이프라인에 오늘 시세를 흘리는 데이터 스레드 하나뿐이라
거기만 `true`를 넘긴다. 지표·기준점·게이트 호출자는 전부 기본값을 쓴다.

**대안 비교**

| 안 | 내용 | 판정 |
|---|---|---|
| `FID_INPUT_DATE_2`를 전일로 | 요청 자체를 전일까지 | 기각 — 휴장·반차 캘린더가 필요하다 |
| **응답 날짜 필터(채택)** | `stck_bsop_date == 오늘`인 행 드롭 | 캘린더 불필요, 장 전/장중/장후 모두 같은 규칙 |
| 갱신 주기 단축 | 스냅샷을 자주 다시 받음 | 기각 — 절단 없이 자주 받으면 기준점이 더 흔들린다 |

장 마감 후에는 오늘 봉이 완성본이라 절단이 하루치 최신성을 버린다. 그래도 절단을 택했다.
전략의 일봉 스냅샷은 08:50~09:00에 받으므로 그 시각엔 오늘 봉이 아직 없어 절단이 사실상 무동작이고,
절단이 실제로 일하는 곳은 장중 재기동·유니버스 재스캔 때의 신규 조회다. 오염이 들어오던 경로가 정확히 거기다.

**배경**: 일봉 조회가 `FID_INPUT_DATE_2`에 **오늘**을 넣어 `output2[0]`이 당일 미완성 봉이다.
그리고 전략의 일봉 스냅샷은 날짜가 바뀔 때만 갱신된다. 두 개가 겹쳐서 "일봉SMA20"이
(i) 오늘 미완성 봉을 포함하고 (ii) 09:00 시점 가격에 고정된 채 종일 안 바뀐다.
09-07 로그에서 `일봉SMA20=107460.0`이 09:44부터 09:58까지 한 번도 안 바뀐 것이 이것이다.

**영향**: 현행에서는 이 값이 넓은 존 게이트(−8%~+5%) 판정에만 쓰여 영향이 작았다.
D-003이 이 값을 분할 매수 가격 결정에 직접 쓰므로 영향이 커진다. D-003보다 먼저 고쳐야 한다.

**근거(로그 산술)**: 08-12 DEVSCALE_161890에서 날짜 경계 없이 10:03→11:06 사이에
현재가가 −1,400 움직일 때 일봉SMA20이 정확히 −70 움직였다. −1,400/20 = −70.
09:33→10:03도 +9,500/20 = +475로 일치한다. 당일 진행 중 봉의 종가(=실시간 현재가)가
SMA20에 1/20 가중으로 들어간다는 뜻이다. 추정이 아니라 실측이다.
정배열 판정에 쓰는 SMA5는 가중이 1/5이라 오염이 4배 크다 — 당일 상승이 스스로 게이트를 연다.

**부수 문제(비결정론)**: 값이 페치 시각에 동결되므로 프로세스 재기동 시각이 기준점을 바꾼다.
같은 날 같은 종목이 재기동에 따라 102,950 / 103,425 / 103,355로 갈렸다(편차 0.46%).
`dev_buy` 1층 폭 0.8%의 58%다. 이 상태로는 오프라인 리플레이가 라이브를 재현할 수 없다.

**수정 방향**: `FID_INPUT_DATE_2`를 전일로 바꾸는 대신 응답에서 `stck_bsop_date`가 오늘인 행을
버린다(휴장 캘린더 불필요). 시그니처에 `include_today=false` 기본값을 두고, 캐시 키에 그 값을 넣는다
— 현재 `daily_cache_`는 키가 ticker 하나뿐이라 절단본과 미절단본이 서로를 덮어쓴다.
절단이 끝나야 "하루 1회 갱신"이 비로소 옳은 설계가 된다. 순서를 뒤집으면 기준점이 더 흔들린다.

**검증 게이트**: 같은 종목·같은 거래일에 09:05와 14:00 두 번 조회해 SMA5/10/20/60이 동일할 것.
`Quant/tools/probe_daily_truncation.py`가 같은 응답으로 절단 전/후 SMA를 나란히 찍는다.

09-07 10:33 장중 실측(모의 도메인, 세 종목 모두 최신봉 날짜 = 당일):

| 종목 | SMA5 Δ | SMA20 Δ |
|---|---|---|
| 005930 | +0.392% | +0.661% |
| 000660 | +0.766% | +0.977% |
| 161890 | −2.061% | +1.356% |

`dev_buy` 1층 폭이 0.8%다. SMA20 오염이 그 **83~170%**로, 감사관이 이격에서 추정한 0.25~0.40%보다
2~3배 크다. 분할 매수 가격에 이 값을 직접 쓰면 1층이 통째로 밀린다.
161890의 SMA5 −2.06%는 정배열 판정에 그대로 들어가는 값이다.

**남은 위험**: 백테스트로 옮길 때 반드시 전일까지 절단해야 한다. 안 하면 오프라인 결과가 낙관 쪽으로 오염된다.
라이브는 시점 t에 t의 가격을 쓰는 것이라 미래정보 참조는 아니지만, 리플레이에서 같은 자리에
당일 종가(15:30 확정값)가 들어가면 그건 교과서적 look-ahead다. 두 경로가 체계적으로 갈린다.

### D-006 분할 매수 교차 가드 — 억제가 아니라 기준점 클램프 (2026-09-07)
**상태**: 채택 (구현·빌드 완료, 라이브 미검증)

**결정**: 분할 매수 기준점을 방향별로 현재가 쪽으로 클램프한다.
매도 밴드는 `max(sma, 현재가)`, 매수 밴드는 `min(sma, 현재가)`를 기준으로 층을 깐다.
베이스 매수는 기준선이 현재가 이상이면 현재가 한 틱 아래로 옮긴다.
스위치는 `ladder_cross_guard`(기본 true).

**배경**: 분할 매수 구성부에 rung 가격과 현재가를 비교하는 코드가 없었다.
기준선이 현재가에서 멀어지면 한쪽 밴드 전체가 현재가를 넘어가 지정가가 아니라 즉시 체결되는

**대안 비교**

| 안 | 내용 | 결과 |
|---|---|---|
| 현행 | 비교 없음 | 이격이 벌어지면 한쪽 밴드가 통째로 즉시 체결. 분할 매수가 아니게 된다 |
| 억제(skip) | 교차하는 층을 건너뜀 | 기각 — 아래 |
| **클램프(채택)** | 기준점을 현재가 쪽으로 당김 | 층 간격 유지, 양쪽 다 지정가로 남음 |

**억제안을 버린 이유**: 처음에 억제로 구현했다가 되돌렸다. 두 가지가 틀렸다.

1. 매도 쪽 전제가 틀렸다. 지정가 매도가 현재가 아래여도 체결가는 지정가 이상(호가에 체결)이라
   투매가 아니다. 억제하면 이격이 벌어진 상태에서 익절이 사라지고 매수만 남는다.
2. 매수 쪽은 베이스가 죽는다. 베이스 지정가가 현재가 위가 되는 조건은 `현재가 < 기준선`인데,
   그건 `add_below_sma_only`가 노리는 눌림 진입 조건 그 자체다. 가장 큰 레그가 눌림에서만 빠진다.

**남은 위험**: 이격이 큰 상태에서 매수 기준점이 현재가를 따라 내려가므로, 하락 추세에서
층이 계속 아래로 재배치된다. 존 게이트(−8% 하한)가 1차 방어지만 데드밴드(D-007)와 같이 봐야 한다.

### D-009 분봉 백필은 1분봉 원본으로 저장 (2026-09-07)
**상태**: 채택 (적용·검증 완료)

**결정**: `PYQuant/data/minute/<ticker>/<YYYYMMDD>.parquet`에 **1분봉만** 저장한다.
3분봉은 저장하지 않고 리플레이 시점에 집계한다.

**배경**: DevScale은 3분봉 위에서 매매하지만 오프라인 3분봉 이력이 없어 백테스트가 불가능했다

**근거**: 1분봉을 원본으로 두면 체결 격자(1분)와 기준점 격자(3분)를 분리해 리플레이할 수 있다.
3분봉만 저장하면 봉 안에서 어느 가격에 닿았는지 알 수 없어 지정가 분할 매수의 체결 판정이 불가능하다.
집계 규칙(`interval_min`)을 바꿔도 다시 받을 필요가 없다는 것은 부수 효과다.

**완결성 게이트**: 초당 한도에 걸리면 빈 응답이 오는데 이것이 "그날 데이터 끝"과 구분되지 않아
하루치가 조용히 잘린다(09-03에 120봉, 09-07에 240봉으로 실제 발생).
페이지 빈 응답은 백오프를 늘리며 세 번 더 두드리고, 저장본이 300봉 미만이면
`<YYYYMMDD>.short.json`에 시도 횟수를 남겨 재개 때 다시 받는다.
거래정지·신규상장처럼 정당하게 짧은 날이 있으므로 재시도는 2회로 막는다.

**검증**: 000660 2026-08-24가 240봉(11:21 시작)에서 381봉(09:00~15:30)으로 복구됐다.

**호출 예산**: 하루 1종목 = 4콜. 40종목 × 246일 ≈ 39,000콜, 약 90분.
장중에는 모의 키가 아니라 실계좌 키로 돌린다 — 초당 한도는 app_key별이라
같은 키를 쓰면 매매 중인 트레이더의 시세 조회를 굶긴다.

### D-011 유니버스·백필 인프라 3건 — 시장 태그 누수, 선정 편향 (2026-09-07)
**상태**: 채택 (적용 완료, C++ 빌드 미검증)

**결정** 세 가지를 함께 고쳤다.

**(1) `kosdaq_enabled` 게이트 누수**
`UniverseScanner`는 후보 티커의 시장을 `universe_scan.json`의 `universe[].market` 태그로만 알았다.
그런데 후보는 파일 축뿐 아니라 KIS 랭킹 3축(시총·거래대금·거래증가율)에서도 들어오고,
그쪽 티커에는 태그가 없다. 태그 없는 티커는 KOSPI로 간주됐으므로 `kosdaq_enabled=false`인데도
코스닥 종목이 통과했다.
조치: `universe_feed.build(with_market_map=True)`가 스냅샷 **전종목** 코드→시장 사전(`market_map`)을
라이브 파일에 동봉하고, 스캐너가 이를 먼저 적재한다. 사전이 있는데도 없는 티커는 `UNKNOWN`으로 두고
코스닥과 같은 보수 판정을 한다(게이트가 닫혀 있으면 드롭). `market_map`이 없는 구 파일에서는
기존 동작을 유지한다. PIT 백필 파일에는 넣지 않는다 — 246일 × 수천 항목이면 산출물만 커진다.

**(2) 분봉 백필의 선정 편향**
`minute_backfill.py --top-n`은 PIT 파일의 **저장 순서** 상위 N이다. `universe_feed`가
시총순 → 거래대금순으로 이어 붙이므로 앞 100개가 전부 시총순이고, `--top-n 40`은 사실상 시장별 시총 top40이었다.
거래대금 축 종목이 한 개도 안 들어온다. 돌고 있던 백필에 09-07 추세 7종목이 0개 포함된 이유다.
이 목록으로 리플레이하면 생존 편향으로 결과가 무효다 — 오늘 시총 상위인 종목은 그동안 오른 종목이다.
조치: 독스트링에 경고를 박고, `--top-n 0`이면 그날 PIT 풀 전체를 쓰도록 했다.

**(3) `--pairs` 모드**
날짜별 대상 종목을 밖에서 지정한다(JSONL 또는 단일 JSON). "그날 실제로 후보였던 종목"만 받으면
호출 예산이 줄고 편향도 없다. 범위 밖 날짜는 버리고 중복 티커는 제거한다.

**대안 비교**

| 안 | 판정 |
|---|---|
| 시장 판정을 KIS 종목정보 API로 개별 조회 | 기각. 후보 수만큼 콜이 늘고 초당 한도를 매매와 다툰다 |
| 태그 없는 티커를 KOSPI로 계속 간주 | 기각. 게이트가 새는 것을 알고 두는 것이다 |
| `market_map`을 PIT 파일에도 동봉 | 기각. 백필은 시장 게이트를 쓰지 않는데 산출물만 커진다 |
| `--top-n`을 거래대금순으로 재정렬 | 기각. 순서를 바꿔도 "무엇이 그날 후보였나"는 여전히 못 고른다. `--pairs`가 상위 호환 |

**검증**: PIT 전량 재생성(`--market ALL --force`) 246일, 미래정보거부 0, 최신일 275종목(KOSDAQ 146 / KOSPI 129).
`--pairs` JSONL·JSON 양식 스모크 통과. **C++ 빌드는 아직 안 했다.** 라이브 `universe_scan.json`에
아직 `market_map`이 없으므로 현재는 하위호환 경로로 동작한다.

**남은 위험**: `market_map`은 스냅샷 시점의 사전이다. 신규 상장·이전 상장 직후 며칠은 `UNKNOWN`으로 떨어져
코스닥 게이트가 닫혀 있으면 드롭된다. 놓치는 쪽으로 틀린다.

**정정 (2026-09-07)**: (1)을 조사하는 과정에서 "라이브 경로에 `KOSDAQ GLOBAL` 시장 태그가 섞여 들어온다"고
적었던 적이 있는데 사실이 아니다. data.go.kr 소스는 `KOSPI`/`KOSDAQ`/`KONEX`만 내보내고,
`universe_feed.build()`는 `market_map`에 `KOSPI`/`KOSDAQ`만 담는다. `KOSDAQ GLOBAL`은 pykrx가 쓰는
KRX 소속부 표기이고 저장소에서는 `site-packages` 안에만 존재한다 — 라이브 경로에 닿지 않는다.
(1)의 본래 근거인 "KIS 랭킹 축 티커에는 태그가 없어 KOSPI로 간주된다"는 그대로 유효하므로 결정은 유지한다.

### D-012 평가지표 교체 — MFE 라벨을 버리고 손절 명시 실현수익으로 (2026-09-07)
**상태**: 채택 (지표 한정. 이 지표로 내린 전략 판정은 D-013)

**결정**: 게이트 평가를 "MFE가 임계에 닿았나"라는 라벨에서, 손절을 명시한 경로 시뮬레이션의
실현수익(R배수)으로 바꾼다. 구현은 [PYQuant/backtest/metrics.py](../PYQuant/backtest/metrics.py).
비교 기준도 pooled 평균에서 **월 동일가중 초과**로 바꾼다.

**배경**: MFE 라벨(20일 내 +15% 도달 ∧ 5일 내 MAE > −6%)로 재면 게이트가 변별되지 않았다.
거래대금 상위 500종목 · 2026년 69,530 종목·일에서 기저 타점률 31.5%, 현행 게이트(존∧정배열)
33.4% — lift 1.06. 기회를 4.9%로 줄이면서 적중률은 1.9%p밖에 못 올린다.
같은 라벨로 "역배열∧5>10∧거래량 5배" 계열이 임계 5단계 단조 증가(5일 +0.76→+4.97%)를 보여
유망해 보였으나, 실현수익으로 재니 기저와 같았다(0.358R vs 0.286R). MFE에는 닿지만 그 전에
손절에 걸린다. 라벨이 손절 경로를 무시하는 것이 원인이다.

**대안 비교**

| 안 | 판정 |
|---|---|
| MFE 임계를 +30%/+50%로 올린다 | 기각. 임계를 올려도 경로를 무시하는 문제는 그대로다 |
| 평균 수익률·승률로 판정 | 기각. 추세 분포는 승률 20~30%·payoff 4~6이라 구조적으로 나쁘게 보인다 |
| 손절 명시 실현수익 R배수 | **채택**. 손절폭이 R의 정의라 게이트끼리 위험 단위가 맞춰진다 |
| pooled 평균으로 게이트 비교 | 기각. 신호가 몰린 달(강세 구간)에 가중돼 착시가 생긴다(아래) |
| 월 동일가중 초과 + 시계열 t | **채택**. 겹침이 흡수되고 87개월 표본으로 부호 일관성을 검정할 수 있다 |

**pooled의 착시**: 6.5년 기준 `정배열∧이격>+5%`는 pooled 0.196으로 기저 0.148을 이기지만,
월 동일가중으로는 초과 −0.092(t=−2.58, p=0.010)로 **유의하게 진다**. 게이트가 강세 구간에
신호를 몰아 내기 때문에 pooled가 부풀려진다. 87개월 중 기저를 이긴 달은 35.6%뿐이다.

**경로 규칙**: 진입 = 신호 다음날 시가. 손절·트레일링은 매일 저가로 먼저 판정하고, 같은 날
고·저가가 둘 다 닿으면 저가를 먼저 맞은 것으로 본다(최악 가정). 갭하락으로 시가가 손절선
아래면 시가 체결. 보유 상한일에 남으면 종가 청산. 비용은 `engine.CostModel`과 같은 왕복 0.31%.

**겹침 보정**: 20일 보유는 인접 신호가 19일 겹친다. 유효표본을 `n/max_hold`로 근사하고 t를
그 기준으로 낸다. 원표본 t보다 보수적이다.

**남은 위험**: 손절폭이 R의 정의라 손절이 다르면 R끼리 직접 비교되지 않는다(같은 규칙 안에서만
비교한다). 유효표본 근사는 보수적인 쪽으로만 틀리도록 잡았고, 정확한 블록 부트스트랩은 안 했다.

### D-013 조건부 필터형 일봉 게이트에 선택 우위가 없다 — 측정 결과 (2026-09-07)
**상태**: 채택 (범위 한정. 편향 감사 지적 반영해 근거표를 PIT 풀로 교체)
**원장**: PIT 상위500 풀 기저 기대R −0.073. 조건부 필터형 일봉 게이트 150조합 중 기저를 유의하게 이긴 것 0개, 정배열 단독은 유의하게 짐(월초과 −0.089, t=−3.92).
**음성결과**: 일봉 조건을 조합해 후보를 좁히는 방향. 새 조합을 들고 오기 전에 이 표부터 본다. 단 이 결론은 "조건부 필터형"에 한정이고 진입가 설계·사이징·포트폴리오 구성은 측정 밖이다.

**결정**: 일봉 조건을 조합해 후보를 좁히는 방향의 작업을 멈춘다. 편향 없는 풀에서 기저를

같은 규칙의 지수가 +17.6%다. **트레일링은 150조합 전부에서 무트레일보다 나쁘다.**
단 R 직접비교는 손절체결률 차이(종목 82.4% vs KOSPI 46.5%)에 오염돼 있으니 크기가 아니라
부호로 읽어야 한다.

**손절폭을 가로지르는 R 비교는 함정이다**: R의 분모가 손절폭이라 손절을 넓히면 같은 손실이
자동으로 작은 R이 된다. 손절 축에서 R과 %의 순위가 정반대다(스피어만 −0.233). R 최고는
손절12%, % 최고는 손절3%다. **R은 손절폭을 고정한 안에서 보유·트레일을 비교할 때만 유효하고,
손절폭 자체를 비교할 때는 기대%로 봐야 한다.** 부호 결론은 어느 쪽으로 봐도 같다.

**단기는 비용 문제가 아니다**: PIT 풀에서 비용을 0으로 놔도 1일 −0.031R, 5일 −0.033R로 음수다
(A게이트 −0.028/−0.048). 실행 개선으로 살릴 수 있는 구간이 아니다. 다만 이 값은 "익일 시가
매수"의 장중 드리프트를 그대로 안고 있고, D-010이 남긴 단서(시가→저가 낙폭 중앙값 2.225%p,
분할 매수가 17.8%만 가져오면 부호 반전)는 아직 이 측정으로 승계되지 않았다.

**빈 칸과 0의 구분**: 매수 행에 0을 쓰면 "0원 실현"으로 읽힌다. 실현이 없는 행은 비운다.

**스키마 승격**: 같은 날 파일에 15열 헤더와 16열 데이터가 섞이면 `csv.DictReader`가 마지막
값을 `None` 키에 넣고 나머지 컬럼이 통째로 어긋난다. 기동 시 헤더가 옛 형식이면 기존 행에
쉼표를 채워 한 번 재작성한다.

**대안 비교**

| 안 | 판정 |
|---|---|
| 대시보드에서만 재구성 | 기각. 당일 전량 매도 종목은 잔고에 없어 평단을 못 구한다(오늘 19건) |
| 별도 실현손익 파일 | 기각. 파일 두 개가 어긋날 때 어느 쪽이 정본인지 정할 방법이 없다 |
| 컬럼 추가 없이 로그 파싱 | 기각. 로그는 로테이션·드롭 대상이라 원장의 정합 보증이 없다 |

**남은 위험**: 컬럼이 오늘 생겼으므로 과거 원장에는 없다. 대시보드는 컬럼이 비면 잔고 평단으로
되짚는 폴백을 유지한다. 폴백도 실패한 건수는 화면에 `*N건 평단미상`으로 표시한다.


### D-018 점수로 비중과 진입 순서를 함께 정한다 (2026-09-07)
**상태**: 채택
**결정**: 횡단면 종합 점수 하나를 두 곳에 쓴다. (a) 슬롯 경합 시 진입 우선순위, (b) 종목별 비중
배수. 점수는 추세·눌림·변동성 세 축의 z-score 가중합이다.

```
S_i = w_t·z(추세) + w_p·z(눌림) − w_v·z(ATR%)        w_t=1.0, w_p=1.0, w_v=0.5
(a) 진입:  rank(S) 내림차순,  rank/total ≤ 1 − (보유슬롯/상한) × 잔여장중비율
(b) 비중:  mult_i = 1 + spread × clamp(z(S_i), −2, +2) / 2       spread=0.6
           mult 전체를 상위 25개 합이 목표 총 베이스(80%)가 되도록 정규화
```

**배경**: 두 가지가 동시에 깨져 있었다.

1. **예산 산술이 안 맞았다.** `base_pct 0.05 × 25슬롯 = 125%`인데 총노출 상한은 95%다.
   진입 단계에서 매수가 무더기로 거부됐다.
2. **슬롯 배분이 선착순이었다.** 57개 전략이 각자 3분봉 존 진입에서 독립적으로 발화하고,
   게이트는 도착 순서대로 25개에서 잘랐다. 점수를 매겨 놓고 점수를 쓰지 않았다.

**왜 z-score인가**: 세 축은 단위가 다르고 날마다 분산이 다르다. 원값을 그냥 더하면 그날 우연히
가장 넓게 퍼진 축이 결과를 지배한다. z-score는 축을 무차원으로 맞추고, ±2σ 클립이 한 종목이
점수를 독식하는 것을 막는다.

**왜 점수 하나로 두 일을 하는가**: 원안은 점수(얼마나 좋은가)와 ATR(얼마나 흔들리는가)을
직교축으로 두고 2단계로 나누는 것이었다. 나눌 실익이 없다 — 효과 귀속은 백테스트에서 축을
꺼 보면 되는 문제지 배선을 나눌 이유가 아니고, ATR은 이미 받아 오는 일봉 조회의 high/low로
계산되므로 REST 호출이 늘지 않는다.

**검산** (자본 6,800만, 57종목, 슬롯 25, base_pct 0.032, max_pct 0.064):

| 점수 분포 | 상위 25 베이스 합 | 배수 최고/최저 | 최상위 베이스 명목 |
|---|---|---|---|
| 정규 | 80.0% | 1.262 / 0.316 | 279만 원 (4.04%) |
| 전 종목 동점 | 80.0% | 1.000 / 1.000 | 218만 원 (3.20%) |
| 좁은 분산 | 80.0% | 1.160 / 0.315 | 252만 원 (3.71%) |

분산이 어떻든 베이스 총합은 80%에 고정된다. 최상위 종목이 분할 매수를 끝까지 태워도 559만 원으로
종목당 명목 상한 800만 원 아래다 — 상한은 백스톱으로만 남는다.

**대안 비교**

| 안 | 판정 |
|---|---|
| 균등 비중 유지 | 기각. 점수가 다른데 비중이 같으면 점수를 매긴 의미가 없다 |
| `max_universe` 100 → 40으로 축소 | 기각. 오늘 정배열 통과가 57개라 100은 아무것도 자르지 않는다. 40은 커버리지만 줄인다 |
| 점수 상위가 오면 최약 보유분을 교체 | 보류. 왕복 비용 0.195%에 분할 매수 리셋까지 얹힌다. 교체 이득이 그보다 크다는 측정이 없다 |
| 배수를 재스캔마다 기존 전략에도 갱신 | 기각. 분할 매수 도중에 예산이 바뀌면 남은 층 예산과 평단이 어긋난다. 신규 등록분에만 적용한다 |
| `score_w_supply` 활성화 | 보류. 수급 로거에 데이터가 아직 없다(D-014) |

**진입 바가 장중에 완화되는 이유**: 기준선은 `1 − (보유슬롯/상한) × 잔여장중비율`이다. 슬롯이
빌수록, 그리고 장 마감이 가까울수록 낮은 랭크도 통과한다. 장 초반에 상위 점수를 위해 슬롯을
비워 두되, 끝까지 안 오면 차선이라도 채운다.

**남은 위험**
- 오프라인 백테스트로 검증하지 않았다. DevScale 3분봉은 PIT 재현·리플레이 하네스가 없어
  forward 적재가 유일한 경로다. 이 결정은 산술 정합(예산·상한)까지만 근거가 있고,
  점수 차등이 실제로 수익을 늘리는지는 아직 측정하지 않았다.
- 잔여장중비율은 09:00–15:00을 선형으로 나눈다. 거래가 시간에 균등하다는 가정인데 실제로는
  개장·마감 근처에 몰린다.
- 슬롯 25가 다 차면 우선순위 로직은 무의미해진다. 그 시점 이후 들어오는 상위 점수 종목은
  교체 없이 버려진다(위 보류 항목).

### D-019 슬롯이 꽉 차도 더 높은 점수는 들어온다 — 교체 진입 (2026-09-07)
**상태**: 채택 (실측 미검증)
**결정**: 동시 보유 슬롯이 꽉 찬 상태에서 더 높은 점수의 종목이 신호를 내면, 보유 중 최약체를
시장가로 비우고 그 자리를 신규 종목에 예약한다. D-018에서 "보류"로 남겼던 항목을 뒤집는다.

**왜 뒤집는가**: D-018은 진입 우선순위 바를 넣었지만 그건 슬롯이 *차기 전에만* 동작한다.
25칸이 차는 순간부터는 "먼저 도착한 순서"가 하루 종일 자리를 지킨다. 점수를 매겨 순서를
정해 놓고 정작 슬롯이 꽉 찬 구간에서 순서를 안 쓰는 셈이었다. 보류 사유였던 왕복 비용은
비용 항목이지 기각 사유가 아니다 — 회전을 묶어서 관리하는 쪽이 낫다.

**동작**:

```
BUY NEW 신호 → 슬롯 꽉참? → 보유분 중 점수 최저(z) 찾기
                              → z 격차 ≥ 0.5σ ?  → 최약체 전량 시장가 매도(DISPLACE)
                                                  → 빈 자리를 신규 종목에 300초 예약
                                                  → 이번 봉 매수는 흘리고, 다음 봉에 예약분으로 진입
```

매도와 매수를 같은 틱에 붙이지 않는다. 매도 체결은 비동기라 같은 틱에 매수를 내면 같은
수량이 `positions_`와 `reserved_`에 동시에 잡혀 총노출이 이중 계상된다. 대신 빈 자리를
예약해 두므로 다음 봉(3분)에 그 종목이 자리를 가져간다.

**회전을 묶는 네 가지 고삐**:

| 항목 | 값 | 이유 |
|---|---|---|
| `displace_min_z_gap` | 0.5σ | 격차가 잡음 수준이면 왕복 비용(약 0.195%)만 나간다 |
| `displace_min_hold_sec` | 900초 | 사자마자 파는 왕복 차단. 기동 시드 보유분은 예외(24시간 전으로 기록) |
| `displace_cooldown_sec` | 1800초 | 밀려난 종목이 곧장 되돌아오는 핑퐁 차단 |
| `displace_max_per_day` | 5회 | 마지막 고삐. 비용이 알파를 먹는 것을 막는다 |

**점수를 모르는 보유분은 건드리지 않는다**: 스캔 유니버스 밖 보유분(청산 관리, 전일 물린
물량)은 교체 후보에서 제외한다. "점수가 없는 것"과 "점수가 낮은 것"은 다르다. 청산 관리가
따로 맡고 있는 물량을 점수 미상이라는 이유로 밀어내면 두 관리 주체가 충돌한다.

**대안 비교**

| 안 | 판정 |
|---|---|
| 그대로 둔다(선착순 유지) | 기각. 슬롯이 차는 순간 점수가 무의미해진다 |
| 매도·매수를 같은 틱에 붙임 | 기각. 매도 체결 전에 매수가 나가면 총노출이 이중 계상된다 |
| 슬롯 예약 없이 그냥 비움 | 기각. 다른 종목이 자리를 가로채면 교체 비용만 치르고 목적을 못 이룬다 |
| 손실 중인 종목 우선 청산 | 기각. 손익은 점수와 무관하다. 손실 중이라는 이유로 파는 건 다른 규칙(손절)의 몫이다 |
| 최약체 부분 매도로 비중만 줄임 | 보류. 슬롯 수는 그대로라 신규가 여전히 못 들어온다. 비중 조정은 이미 D-018의 배수가 한다 |

**검증**: `test_order_gate` 단위 테스트 6건 — 최약체 선택, 격차 미달 차단, 점수 미상 보유분
제외, 최소 보유 시간 차단, 슬롯 예약·쿨다운, 일일 상한. 전부 통과.

**남은 위험**
- **실장에서 재보지 않았다.** 단위 테스트는 규칙대로 동작하는지만 본다. 교체가 실제로
  수익을 늘리는지는 측정하지 않았다. 임계 0.5σ와 하루 5회는 근거 없는 초기값이다.
- 교체 매도는 시장가다. 유동성이 얕은 코스닥 종목에서 슬리피지가 0.195%를 넘길 수 있다.
- 최약체가 분할 매수 2층까지 태운 종목이면 그 예산이 통째로 리셋된다. 분할 매수 진행도를
  교체 판정에 넣지 않았다.
- 다음 봉까지 300초 예약을 잡는데, 그 사이 신규 종목의 존 조건이 깨지면 슬롯이 빈 채로
  예약만 만료된다(교체 비용은 이미 나간 뒤).

### D-020 장 종료 후 일지·대시보드 자동화를 결정론 스크립트로 옮김 (2026-09-07)

| 대안 | 판단 |

"보존"만 기록한다. 마커가 있는 자동 생성분만 최신 로그 기준으로 다시 만든다. 자동화가 수기 기록을

**남은 위험**

### D-021 국면 판정 파라미터를 config로 뺀다 — 검증할 수 없던 분기를 태우기 위해 (2026-09-07)

**날짜**: 2026-09-07

**결정**: `RegimeController::Config`(지수코드·이평기간·점수 임계값·fail_fallback_n)를
config `"regime_tuning"`으로 주입할 수 있게 배선했다. 미지정이면 기존 기본값 그대로다.
점수 임계값 오버라이드는 실계좌(`kis.is_paper=false`)에서 무시하고 ERROR를 남긴다.

**왜 바꿨나**

라이브 15거래일이 전부 NEUTRAL이었다. 분류기 문제가 아니라 시장이 그랬던 것인데
(2005~2026 5,349거래일 분포는 BULL 41.6% / NEUTRAL 37.6% / BEAR 20.8%로 정상),
결과적으로 BULL·BEAR 분기가 한 번도 실행되지 않았다. 그 상태로 실계좌에 올리면
처음 도는 코드가 실계좌에서 처음 돈다.

그런데 태울 방법이 없었다. `Engine::start()`가 `make_unique<RegimeController>()`로
기본값 인스턴스를 만들고, main.cpp는 `regime_strategies`와 `regime_reeval_sec`만 읽었다.
임계값은 물론 **지수코드마저 하드코딩**(`"0001"` 코스피)이라 코스닥 지수로 판정하고 싶어도
코드를 고쳐야 했다. 검증 수단이 없다는 것과 별개로, 이건 그냥 빠진 설정이다.

**갈랐던 지점**

| 대안 | 판단 |
|---|---|
| 테스트 전용 `set_regime_for_test(Regime)` | 기각. 분류기·evaluate()를 건너뛴다. 정작 태우려던 배선을 안 태우니 검증 가치가 낮다 |
| config `regime_force: "BEAR"` | 기각. 판정을 통째로 우회. 프로덕션 config에 남으면 국면이 상수로 굳는다 |
| **`Config`를 config.json에 노출** | **채택.** 분류기를 실제로 태우고, 원래 있어야 할 설정을 메운다 |

**어떻게 태우는가**

2026-09-07 코스피 실측 score는 1이다(종가>200MA에서 +1, 이평 혼조로 0).
`score_bull_threshold: 1`이면 그 1이 BULL로, `score_bear_threshold: 1`이면 BEAR로 떨어진다
(`classify()`가 BULL을 먼저 보므로 BEAR 쪽은 bull을 기본 +2로 둬야 한다).
가짜 봉도 우회 경로도 없이 실제 시장 데이터로 두 분기를 다 지나간다.

**오분류를 막는 장치**
- 기동 시 유효 파라미터 전체를 INFO로 찍는다. 임계값이 기본값과 다르면 WARN을 덧붙인다.
- 실계좌에서는 임계값 오버라이드를 무시하고 기본값으로 되돌린다(ERROR 기록). 지수코드·이평
  기간은 정당한 튜닝이라 막지 않는다.
- `bull <= bear`면 `classify()` 순서상 NEUTRAL이 도달 불능이 되므로 기본값으로 되돌린다.

**곁가지로 나온 문서 정정**

배선을 보다가 CLAUDE.md가 두 국면 축을 뒤바꿔 적어둔 것을 찾았다. "BEAR 등에서는 보유 전량을
시장가로 청산하는 FORCE_LIQ 신호를 낸다"고 되어 있었는데, `force_liquidate_`를 세우는 곳은
`Engine.cpp:1070` 하나뿐이고 입력은 `regime.json`이다. `RegimeController`의 BEAR는 전략 집합만
고른다. 하락장에서 이 문서를 믿고 "BEAR면 청산되겠지" 하고 있으면 청산은 일어나지 않는다.
CLAUDE.md와 DEFERRED_ISSUES D-15를 같이 고쳤다.

### D-022 강한 추세 종목용 추세확장(TRENDX) 슬리브를 눌림 슬리브와 동시에 돌린다 (2026-09-08)
**상태**: 채택 (모의 실증 단계. 비중으로 리스크를 조절한다)
**원장**: 눌림 슬리브가 과확장컷(`max_dev_pct=0.05`)으로 버리던 이격 +5%~+35% 구간을 두 번째 슬리브가 받는다. 두 슬리브의 유니버스는 이격 밴드로 상호배타다.
**결정**: `DEVIATION_SCALE`을 두 벌 등록한다. 눌림(DEVSCALE, 이격 −8%~+5%)과 추세확장(TRENDX, +5%~+35%)이
동시에 돌고, 각자 자기에게 맞는 종목을 고른다.

**배경**: 09-08 스캔에서 정배열을 통과한 61종목 중 48종목(79%)이 과확장컷에 잘렸다. 눌림 전략 하나만 돌리는 한
강한 추세 종목은 구조적으로 매매 대상이 될 수 없다. 코드에도 막는 곳이 둘 있었다. (1) 존 하단이
`-pullback_pct`로 하드코딩돼 SMA20 위의 진입 밴드를 표현할 방법이 없었다. (2) 분할 매수 기준점이
`min(SMA20, 현재가)`라, 이격이 벌어진 종목은 매수층이 시장가보다 5~35% 아래에 깔려 하루 종일 안 붙는다.
`entry_lower_pct`·`anchor_on_price`로 둘 다 열었다. 엔진의 재스캔 슬롯도 하나뿐이라 두 번째
`set_universe_rescan`이 첫 번째를 조용히 지웠다 — 슬리브별 job 벡터로 바꿨다.

**대안 비교**: 새 전략 클래스를 만드는 안은 분할 매수·리프라이스·청산 경로를 통째로 복제하게 되어 버렸다.
과확장컷 값만 키우는 안은 눌림 슬리브의 성격을 흐려 두 종목군이 같은 파라미터를 나눠 쓰게 된다.

**근거**: 같은 표본에서 이 종목군의 우위는 측정되지 않았다(아래 남은 위험). 그럼에도 돌리는 이유는,
과거 일봉 지표로 측정할 수 있는 것이 조건부 필터형 선택 우위뿐이고(D-013) 진입가 설계·사이징은 그 측정
바깥이기 때문이다. 판정을 실매매 표본으로 옮기고 비중으로 손실을 제한한다.

**남은 위험**: `dev>5%` 풀에서 13피처×5구간 어느 것도 Bonferroni 보정 후 살아남지 못했고, 같은 날 짝지은
비교 20칸 중 양수는 3칸뿐이며 h20은 4/4 구간에서 유의하게 음수였다. 즉 **이 슬리브는 엣지가 확인된 것이
아니라 확인하려고 여는 것**이다. 그래서 슬리브 전체 비중을 작게 잡고 5종목으로 시작한다.

비중 다이얼은 `weight_target_pct` **하나**다. `score_to_mult`가 슬리브의 베이스 명목 합계를
`weight_target_pct`에 맞춰 정규화한 뒤 스코어 비례로 종목에 나눠 주므로, `base_pct`·`max_pct`는
종목당 절대 금액이 아니라 **베이스 대 물타기의 비율**만 정한다. 처음에 종목당 금액으로 읽고
0.015/0.022를 한도로 착각했는데, 실측은 그렇지 않았다 — 09-08 13:05 금호건설 베이스 167주×16,090원
= 269만원으로 `base_pct`(자본의 1.5% ≈ 152만원)의 1.77배였다(스코어 1위라 mult가 컸다).

지금 값 `weight_target_pct=0.10`은 슬리브 베이스 합계 자본의 10%, 물타기까지 다 채우면
`max_pct/base_pct` 비율만큼 늘어 **최대 약 15%**다. 손실이 쌓이면 이 값을 줄인다.

이미 반대해 뒀는데, 레이어를 더하는 안들은 거기 걸리고 유효 구간을 줄이는 안은 걸리지 않는다.

설계를 한 줄로 하면 이렇다 — **장중 정보가 없는 축은 장중 거부권을 갖지 않는다.**

**미결**: `HALT_SCORE` 값. 로그 전 구간에서 `ENTRY_HALT` 토글은 6건/4거래일뿐이고 그중 진입이
활성이던 날은 09-10 하루다. `score=−3`이 5건, `−4`가 1건이므로 −4는 관측된 halt의 83%를 없앤다.
이건 미세조정이 아니라 사실상 게이트 해제이고 근거는 하루다. 다만 이 점수는 FDR 일봉 5개의 결정론
함수라 **다년 재구성으로 셀 수 있다.** 셀 수 있는 것을 안 세고 하루로 정한 것이 이번의 실제 결함이다.
재구성(연도별 −3/−4 발동일수, 발동일의 코스피 T+1 수익률 분포)이 나올 때까지 −4는 잠정값이다.
재구성 시 look-ahead 두 곳을 주의한다 — KST T일 아침에 보이는 미국 종가는 T−1 세션이고,
USD/KRW는 동일 세션이라 종가를 쓰면 그날 09:00 게이트에 미래정보가 들어간다.

**같이 드러난 것(이 결정 밖)**: 09-10에 13:08 해제 후 첫 BUY 접수까지 66분 47초가 걸렸는데
그 사유는 halt가 아니라 `대체 주문 보류 — 직전 취소가 대상 없음` 176건이다(09-09 16건의 11배).
취소-대체 상태기계 교착이 이 날의 실질 병목이다. 국면 축과 별개로 잡는다.
이 가드(`OrderRouter`의 `cancel_miss_`)는 커밋 전 변경에서 새로 들어온 것이라 176건은 그 변경의
회귀였고, 보류에 10초 시간 상자(`kCancelMissGuardSec`)를 씌워 스스로 풀리게 했다.

### D-035 재기동 직후 한도 거부는 호출을 줄여서 막고, 취소할 것이 없는 취소는 거부로 세지 않는다 (2026-09-11)
**상태**: 채택

**결정**: 여섯이다.

1. DevScale `fetch_equity()`는 프로세스 공용 일간 캐시다. 총평가금은 계좌 하나의 값이라 종목 스레드마다
   부를 이유가 없다. 첫 성공을 그날 값으로 쓰고 실패(0)는 캐시하지 않는다.
2. 주문 스레드의 발주 간격(`order_min_interval_ms`)은 **KIS를 실제로 부른 뒤에만** 센다.
   `OrderRouter::kis_calls()` 누적 카운터를 submit 전후로 비교한다. 게이트·ENTRY_HALT의 로컬 거부는
   한도와 무관하다.
3. 전략이 신규매수 차단(`OrderGate::is_entry_halted`)을 계획 단계에서 읽는다(`StrategyBase::entry_halted`).
   DevScale은 차단 중 매수 rung을 걷고 풀리면 시그니처가 바뀌어 다시 깐다. 차단이 켜지면 살아 있던
   매수 예약도 취소된다 — 이 부수효과는 D-033 체류가 떨림을 막는 것으로 받는다.
4. `scan_itb`의 코스피 게이트도 `latch_risk_off`를 쓴다. 래치는 ITB 전용(`g_itb_kospi_latch`)이라 DevScale
   판정과 섞이지 않는다. 기본값은 재개 임계=차단 임계·체류 0으로 옛 동작과 같다 — 값을 가르는 것은
   사용자 승인 사항이라 config에 남겼다(`risk_off_resume_pct`·`risk_off_dwell_sec`).
5. 미체결 부속 파일(`open_orders.txt`)은 기동 때 비우지 않는다. 읽은 줄을 `carry_rows_`에 들고
   스냅샷마다 이번 세션 줄과 합쳐 쓰고, 취소가 접수되거나 이미 종료로 확인된 줄만 뺀다. 한도 거부로
   남긴 줄·취소를 마치기 전에 죽은 줄이 다음 재기동에 그대로 넘어간다.
6. 취소 대상이 없는 취소 요청(거부된 rung·이미 취소·이력 없음)은 `REJECTED`가 아니라 `CANCELLED`로
   닫는다. 로그는 INFO `취소 불요`, 거부 통계에 안 들어간다. 체결 흔적이 있는 경우만 WARN과
   신규매수 보류(`cancel_miss_`)를 유지한다.

거부됐다. 원인은 종목 스레드 ~40개가 같은 잔고를 동시에 부른 것이었다(1·2 적용 뒤 09:44 재기동:

### D-037 테스트를 ctest에 묶고, WS 채널 파서는 헤더 전용 순수 함수로 꺼내 테스트한다 (2026-09-11)

1. `Quant/tests/`의 실행형 테스트 11개를 `enable_testing()`/`add_test()`로 등록한다. 루트 `CMakePresets.json`에

3. `KisWebSocket`의 채널 파서 6종(현물 호가·체결, 선물 호가·체결, 미국 체결, 체결통보)은 필드 위치·최소 길이·숫자

   흘리고, 체결통보는 버린다.

   틀린 문장이라 교체한다.

**배경**: 테스트 12파일·어서션 약 200개가 있는데 등록이 없어 손으로 하나씩 돌렸고, 문서는 없다고 적혀 있었다.

`WebSocketClient.cpp` 안에 진단 로그와 섞여 있어 WinHTTP/BCrypt 없이는 부를 수 없었다.

**대안 비교**:

### D-039 주문 결과는 한 값에 담고, 숫자 필드는 전부 소비했을 때만 받는다 — 계약 표현 정리 (2026-09-11)
**상태**: 채택 (`Quant/src/core/Engine.cpp`·`Quant/include/risk/OrderGate.h`는 D-036 커밋 뒤 같은 번호로 잇는다)

**결정**: 넷이다.

1. `IOrderExecutor`의 주문·취소·정정은 모두 `OrderAck{odno, krx_orgno, err_code}`를 돌려준다. `ok()`는
   `!odno.empty()`이고, 실패면 `err_code`가 비지 않는다(KIS `msg_cd`, 응답이 없거나 못 읽으면
   `kis_err::kTransport`, `rt_cd≠0`인데 `msg_cd`가 없으면 `kUnknown`). 빈 문자열을 돌려주고 사유는
   `last_order_error_code()`로 따로 묻던 부채널과, 본문이 같은 사본이던 `submit_order(string)`은 지운다.
   `submit_order_ack`가 순수 가상이고 `[[nodiscard]]`다 — 접수 여부를 모른 채 넘어가는 경로가 컴파일 때 드러난다.
2. 스레드·뮤텍스를 소유한 클래스(`Engine`·`KisWebSocket`·`OrderRouter`·`ZmqBridge`·`Logger`·`KisClient`·
   `RegimeController`·큐 3종)는 복사 생성·대입을 `= delete`한다. 큐 3종의 `push`/`pop`은 `[[nodiscard]]`이고
   `RingBuffer::push`는 `T`의 복사·이동이 던지지 않을 때만 `noexcept`다(`MarketData`는 `std::string`을 품어 조건부).

3. `kis_ws::detail::to_double/to_i64/to_int`는 `std::from_chars`로 바꾸고 문자열 전체를 소비했을 때만 성공한다.
   `"215000abc"`·`"1,000"`은 실패(`kBadNumber`), 앞의 `'+'`는 KIS 부호 표기라 허용한다. 부동소수 `from_chars`가
   없는 표준 라이브러리(GCC 10 이하)는 `strtod`로 대신하되 같은 규칙을 지킨다.
4. 전략 4종(`FixedInterval`·`PriceTarget`·`Theme`·`ValueContrary`)에 각각 있던 `parse_hhmm` 사본을 지우고
   `krx::parse_hhmm`(`Quant/include/core/MarketSession.h`)을 부른다.

**배경**: 접수 실패가 빈 문자열이고 사유는 `KisClient` 멤버 `last_order_msg_cd_`에 남아 호출부가 두 번
물었다. `OrderRouter`는 `kis_.last_order_error_code()`를 세 곳에서 읽었고, 그 값은 "직전 호출"에 묶여 있어
호출 순서가 바뀌면 다른 주문의 사유가 붙는다. `submit_order`와 `submit_order_ack`는 60줄이 같은 사본이라 한쪽만
고치면 갈라진다. 큐의 `push` 결과를 버리면 가득 찬 큐에서 메시지가 조용히 사라지는데 컴파일러가 아무 말도 하지
않았다. `stod`는 `"215000abc"`를 215000으로 받아 전문 한 칸이 밀린 레코드가 그럴듯한 값으로 통과했다
(`_private/code_upgrade/CPP_LEVEL_AUDIT.md` 4절).

**대안 비교**:

| 안 | 판정 |
|---|---|
| `std::optional<std::string>` 반환 + 부채널 유지 | 기각. 실패 사유가 여전히 다른 곳에 있어 호출부가 두 값을 맞춰 읽어야 한다 |

| `to_*`를 예외 없는 `strtod`만으로 | 기각. `strtod`는 앞 공백을 건너뛰고 로케일을 본다. `from_chars`는 셋 다 없고 할당도 없다 |

**확인 방법**: `Quant/tests/test_ws_decode.cpp`가 `"215000abc"`·`"1,000"`을 `kBadNumber`로, `"+215000"`을
`kOk`로 고정한다. `Quant/tests/test_order_router.cpp` 스텁은 `OrderAck::fail(err_code)`로 실패를 내고
`blocked_sell_releases_reservation`이 `40240000` 경로를 그대로 통과한다. `ctest --preset x64-release` 11/11.
`Quant/tools/manual_order.cpp`는 `ack.err_code`를 화면에 찍는다. 실행 중 `quant_trader`는 재빌드하지 않았다.

### D-042 WS 프레임은 원문을 가리키는 뷰로 나누고, 링버퍼 인덱스는 마스크로 얻는다 — 수신단 할당 제거 (2026-09-11)
**상태**: 채택 (`Quant/src/core/Engine.cpp`·`OrderGate` 쪽 종목 ID 인터닝·키 구조체는 D-036 커밋 뒤 C-5 후반으로 잇는다)

**결정**: 넷이다.

1. `KisWebSocket::parse_message`는 프레임을 `std::string` 벡터로 자르지 않는다. `kis_ws::split_fields`가
   원문 `msg`를 가리키는 `string_view` 벡터(`parts_`·`fields_`, 수신 스레드 소유, 용량 재사용)를 채우고,
   디코더 6종은 `kis_ws::Fields{data, count}`(16바이트 뷰)를 받는다. 다건 프레임은 `kis_ws::Records`가
   구간만 가리킨다 — 레코드마다 벡터를 만들지 않는다. 뷰는 `msg`가 사는 함수 범위 안에서만 쓰고, 복호
   평문은 같은 범위의 `plain`에 둔다.
2. 채널별 "첫 수신" 진단 로그는 종목마다가 아니라 채널마다 한 번이다. 틱마다 `std::set<std::string>`을
   찾던 조회가 빠진다. 전문 필드 순서를 실데이터로 확인하는 용도라 채널당 한 줄이면 족하다.
3. `RingBuffer`는 용량을 2의 거듭제곱으로 올리고(`1024→1024`, `1000→1024`) 인덱스를 `& mask_`로 얻는다.
   `head_`·`tail_`은 감싸지 않는 누적 카운터라 full/empty 구분용 빈 슬롯이 없고, `size()`는 `head - tail`
   하나다. `capacity()`는 실제 슬롯 수를 돌려준다.
4. `OrderRouter::next_id`는 `ostringstream` 대신 고정 버퍼 `snprintf`다. 주문마다 부르는 곳이다.

**배경**: 호가 프레임 한 장(59필드)이 `split_str` 두 번으로 `std::string` 60여 개를 만들었고 토큰은 문자
단위 `+=`로 자랐다. `COUNT`는 `stoi`+`try/catch`였다. 링버퍼는 `% capacity_` 나눗셈이 push·pop마다 있었다
(`_private/code_upgrade/CPP_LEVEL_AUDIT.md` 3절·7절).

**대안 비교**:

| 안 | 판정 |
|---|---|
| `std::vector<std::string>`을 두고 `reserve`만 | 기각. 토큰 문자열 자체의 할당이 남는다(SSO를 넘는 필드가 있고, 벡터 재사용도 요소 소멸을 부른다) |
| 디코더를 컨테이너 템플릿으로 | 기각. 테스트가 `vector<string>`으로 부르는 편의를 위해 헤더에 템플릿을 두면 계약이 흐려진다. 테스트 쪽 어댑터 `V` 한 줄로 충분하다 |
| 뷰 벡터를 함수 지역 변수로 | 기각. 프레임마다 벡터 할당이 다시 생긴다. 수신 스레드 하나만 만지므로 멤버가 맞다 |
| 링버퍼 용량을 사용자가 준 값 그대로 두고 나눗셈 유지 | 기각. 엔진의 큐 4개는 이미 2의 거듭제곱(1024·256·4096·4096)이라 올림으로 커지는 곳이 없다 |
| 종목 ID 인터닝(`SymbolId`)까지 한 번에 | 보류. `TradeData`·`OrderBook`에 ID를 실으려면 `Engine.cpp`·전략 등록·`OrderGate` 키가 같이 바뀌어야 하고 그 파일들은 D-036이 쥐고 있다 |

**확인 방법**: 같은 59필드 호가 프레임을 30만 번 자르고 디코드하는 마이크로벤치(임시 파일, 리포 밖)에서
프레임당 4,440ns → 690ns(6.4배), 체크섬 동일. `docs/reports/PIPELINE_LATENCY_REPORT.md` 결과 ④.
`Quant/tests/test_ws_frame.cpp`는 뷰의 수명 함정을 그대로 드러냈다 — 임시 벡터에서 만든 뷰를 식 밖에서
읽어 첫 실행에 실패했고, 벡터를 잡아 두는 형태로 고쳤다. `Quant/tests/test_ringbuffer.cpp`에 용량 올림·
가득 참·마스크 경계 케이스를 더했다. `ctest --preset x64-release` 13/13. 실행 중 `quant_trader`는 재빌드하지
않았다(주문·수신 경로는 장 종료 후 재기동).
