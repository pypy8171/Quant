# 프로세스 경계 실측 리포트 — 나누면 얼마가 들고, 고장은 언제 알아채는가

> 하네스: [Quant/tests/bench_peer_failure.cpp](../../Quant/tests/bench_peer_failure.cpp)
> 측정일: 2026-09-22 / 빌드: Release(NDEBUG), Ninja+MSVC / 머신: Windows 11, 16 HW threads
> 목적: 전략과 주문·원장을 다른 프로세스로 나누는 설계(D-071 큐 34)의 근거 숫자를 만든다.

## 왜 쟀나

그동안의 벤치는 전부 **잘 돌 때 얼마나 빠른가**를 쟀다([PIPELINE_LATENCY_REPORT.md](PIPELINE_LATENCY_REPORT.md)).
프로세스를 나누려는 이유는 속도가 아니라 **고장 격리**다 — 지금은 전략 코드 한 곳이 죽으면 주문·원장까지
같이 죽어서, 내던 주문을 마치지도 기록하지도 못하고 끝난다. 그래서 이 리포트가 답하는 질문은 두 개다.

1. 나누면 시세 한 건을 넘기는 데 얼마가 더 드나
2. 한쪽이 죽었을 때 남은 쪽이 **언제** 알아채나

## 용어

| 표기 | 뜻 |
|---|---|
| p50 / p99 / p999 | 중앙값 / 상위 1%가 시작되는 선 / 상위 0.1%(꼬리) |
| crash | 정리 없이 죽는다. 전략 코드의 미처리 예외·접근위반과 같은 자리 |
| exit | 정상 종료 |
| hang | 프로세스는 살아 있는데 일을 멈춘 상태(무한루프·교착) |
| 심장박동(heartbeat) | 살아 있다는 표시를 정해진 간격으로 찍어 두고, 그게 끊기면 죽었다고 보는 방식 |

단위: µs=마이크로초(100만분의 1초), ms=밀리초(1,000분의 1초).

## 측정 조건

같은 머신의 두 프로세스다. 공유메모리(Windows `CreateFileMapping` / POSIX `shm_open`)로 붙였고,
심장박동 간격 200µs, 시간초과 문턱 5ms, 자식은 300ms 살아 있다가 정해진 방식으로 죽는다.

> 측정 범위 주의: 브로커 왕복·주문 취소 응답은 들어 있지 않다. 재는 것은 "남은 쪽이 상대의 죽음을
> 알아챌 때까지"와 "공유메모리로 레코드 한 건을 넘기는 비용"이다.

## 결과 ① — 경계 통과 지연

레코드 84바이트(캡처 파일의 체결 한 건과 같은 크기), 97,219건.

| 전달 방식 | p50 | p99 | p999 | max |
|---|---|---|---|---|
| **공유메모리** | **0.1µs 미만** | 0.10 µs | 1.50 µs | 55.2 µs |
| TCP loopback (결과 ③, 2026-09-02) | 15.5 µs | 27.7 µs | 609 µs | 1.91 ms |

**판정: 시세 데이터 통로는 공유메모리다.** TCP·ZMQ는 p50에서 150배, 꼬리에서 400배 비싸다.
지금 있는 [ZmqBridge](../../Quant/include/ipc/ZmqBridge.h)는 관측용(JSON 문자열, 이벤트마다 문자열 하나)이라
초당 수만 건이 흐르는 데이터 통로로는 쓸 수 없다 — 관측 통로로 남기고 데이터 통로는 따로 낸다.

## 결과 ② — 죽음 감지 지연

마지막 생존 신호에서 남은 쪽이 알아채기까지.

| 죽는 방식 | OS 종료 알림 | 심장박동 시간초과(문턱 5ms) |
|---|---|---|
| crash | **1,385 ms** | 5.0 ms |
| exit | 2.6 ms | 5.0 ms |
| hang | **못 잡음** | 5.0 ms |

**이 표가 이 리포트의 핵심이다.** 세 가지가 읽힌다.

- **crash를 OS 알림으로 기다리면 1.4초 늦다.** 프로세스가 정리 없이 죽으면 Windows 오류 보고(WerFault)가
  붙어 프로세스 개체가 그만큼 늦게 신호된다. 하필 crash가 가장 급한 경우인데 가장 늦게 안다.
- **hang은 OS가 아예 말해주지 않는다.** 그런데 전략 코드에서는 crash보다 hang이 더 흔하다 — 무한루프,
  교착, 외부 호출 대기. 이것만으로도 "OS가 알려주겠지"는 설계 근거가 못 된다.
- **심장박동은 셋 다 문턱 값 그대로 잡는다.** 5.000ms에 흔들림이 없었다. 문턱은 그대로 설계에서 고를
  값이라는 뜻이고, 더 줄일 여지가 있다(아래 남은 것).

**판정: 감지 수단은 심장박동이다. OS 종료 알림은 보조로만 쓴다.**

## 결과 ③ — 기록하고 내려가는 비용

주문 한 건을 디스크에 확실히 남기는 비용(append + flush), 64바이트 × 500회.

| 구간 | p50 | p99 | p999 | max |
|---|---|---|---|---|
| write + flush | 347 µs | 703 µs | 885 µs | 885 µs |

미결 주문 30건을 기록하고 내려간다면 대략 10ms다. 감지 5ms를 더해 **15ms 안에 마무리가 끝난다.**
지금 구조에서 같은 상황에 남는 시간은 0이다 — 주문 쪽도 같이 죽으니까.

이 347µs는 **운영체제 캐시까지 비우는**(Windows `FlushFileBuffers`) 값이다. 지금 원장 저널의 기본 설정은
거기까지 가지 않고 `fflush`에서 멈춘다(`ledger_journal_fsync`가 false) — quant-9d가 같은 기계에서 잰 값으로
p50 6.9µs다. 그래서 **오늘 주문 한 건이 내는 비용은 6.9µs이고, 347µs는 "확실히 남기기"를 켰을 때의 값**이다.
마무리 10ms 계산은 확실히 남기는 쪽을 쓴 수치다 — 내려가는 길에는 캐시에만 있는 기록이 의미가 없어서다.

## 캡처 입력의 실제 모양 (09-21 하루)

`PYQuant/data/ticks_raw/ticks_1789947365.bin`, 74.9 MB.

| 항목 | 값 |
|---|---|
| 레코드 | 891,670건 — **전부 체결, 호가 0건** |
| 종목 | 39개(KIS 구독 상한 40에서 체결통보 1칸 뺀 수) |
| 초당 건수 | p50 23 · p99 252 · 최대 1,059 |

두 가지를 적어 둔다. **호가가 한 건도 안 잡혀 있다** — 지금 캡처는 체결만 받는다. 호가는 한 건이
212바이트로 2.5배 무겁고 건수도 많아, 경계를 넘길 실제 양은 이 표보다 훨씬 크다. 그리고 이 39종목은
가장 활발한 종목들이라 **여기에 2,700/39를 곱하면 과대추정**이다. 전 시장 규모 수치는 이 파일로 못
내고, [PIPELINE_LATENCY_REPORT.md](PIPELINE_LATENCY_REPORT.md)의 Zipf 분포 가정이나 합성 부하로 재야 한다.

## 설계에 바로 들어가는 것 (D-114 입력)

1. 시세 통로는 공유메모리 링. 전송 형식은 캡처 파일 레코드와 같은 바이트로 둔다 — 파일 형식과 경계
   형식이 하나면 리플레이·백테스트가 그대로 따라온다.
2. 전략→주문 방향은 시세와 반대 성질이다(초당 몇 건, 한 건도 잃으면 안 됨, 받았다는 응답 필요).
   같은 기계를 쓰지 않는다.
3. 살아 있는지는 심장박동으로 본다. OS 종료 알림은 보조.
4. 체결통보(H0STCNI)는 지금 시세와 같은 WebSocket 세션에 실려 있다
   ([WebSocketClient.cpp:474](../../Quant/src/api/WebSocketClient.cpp#L474)). 주문 프로세스가 혼자 남아
   마무리하려면 체결을 계속 들어야 하므로, 체결통보 구독은 주문 프로세스가 자기 세션으로 가져간다.
   세션 여럿은 이미 돌아간다(`FeedMux`·`quote_kis`).
5. 손절 판단이 전부 전략 안에 있다(전략 헤더 4개 + `SignalDispatcher`). 전략이 죽으면 보유분을 지킬
   것이 없다. **보호 주문(청산선)을 주문 프로세스에 미리 등록**해 두는 것이 분리의 가장 큰 실익이다.
6. 원장 저널은 주문 프로세스가 소유하고 캡처 파일과 섞지 않는다 — 요구가 다르다. 캡처는 흘려 써도 되고
   (flush 없음), 원장은 한 건마다 확실히 남겨야 한다(위 347µs). 주문·리스크는 단일 시퀀서라는 원칙 4와
   같은 이유다.

## 남은 것

- **심장박동 문턱을 얼마로 할지**는 아직 못 정한다. 위 5ms는 임의로 고른 값이고, 흔들림이 없었던 것은
  자식이 아무 일도 안 하고 있었기 때문이다. 전략 프로세스가 전 시장 부하를 받는 동안 박동 간격이 얼마나
  흔들리는지를 재야 문턱을 정할 수 있다. 그 전에는 오탐(살아 있는데 죽었다고 판정)을 계산할 수 없다.
- crash 감지 1.4초는 오류 보고를 끄면 줄어든다. 얼마나 줄어드는지는 안 쟀다.
- 호가를 켠 캡처가 없다. 캡처 v2에서 같이 잡고 이 표를 다시 채운다.
