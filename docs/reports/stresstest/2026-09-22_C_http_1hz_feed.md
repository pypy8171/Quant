# C회차 — 전 종목 1초 피드로 전략·주문까지 (2026-09-22 장중)

## 1. 무엇을 물었나

앞선 1차·A회차·B회차는 전부 **합성 유량**이었다. 하네스가 종목 2,700개어치 체결을 만들어 밀고 엔진이 그것을
받아냈다. 답한 질문은 "2,700종목 규모의 부하를 단일 프로세스가 견디는가"였고, 답하지 못한 질문이 남았다.

> **2,700종목 시세를 실제로 1초마다 받아서, 전략을 돌리고, 주문까지 낼 수 있는가.**

KIS WebSocket은 세션당 41종목이라 이 질문에 답할 길이 없었다. 전 종목 시세를 주기마다 HTTP로 통째로 받는 피드를
붙여 실제 장에서 쟀다.

## 2. 어떻게 쟀나

- **언제**: 2026-09-22(화) 14:54–15:05 KST, 정규장 중
- **무엇을**: `Quant/config/universe_full.json` 앞 2,700종목
- **피드**: `Quant/src/core/HttpQuoteFeed.cpp`. 수신 스레드 4개가 각자 675종목을 맡아 한 요청으로 받는다
  (한 바퀴에 요청 4번). 종목은 목록 자리로 스레드가 정해지고 도는 동안 안 바뀐다 — 한 종목은 한 스레드만 낸다.
- **체결로 바꾸는 규칙**: 주기 사이에 늘어난 누적 거래량이 그 건의 수량이다. 값이 그대로면 그 주기에 체결이
  없었다는 뜻이라 흘리지 않는다. 첫 바퀴는 기준만 잡고 버린다.
- **전략**: 종목마다 `IntradayBreakoutStrategy` 하나, 2,700개. 채널 2분. 장시계는 합성이 아니라 응답에 실려 온
  실제 체결 시각이다.
- **명령**:
  ```powershell
  .\Quant\build_win\bench_engine_load.exe run --tickers 2700 --lanes 4 --shards 4 --seconds 300 `
      --source http --sweep-ms 1000 --strategy itb --channel-min 2 `
      --out docs\reports\stresstest\data\2026-09-22_C_http_1hz.csv
  ```
- **원자료**: [data/2026-09-22_C_http_1hz.csv](data/2026-09-22_C_http_1hz.csv) ·
  [data/2026-09-22_C_http_7s.csv](data/2026-09-22_C_http_7s.csv)
- **빌드 주의**: 이 회차를 낸 `Quant/build_win`이 헤더 의존을 안 적고 있었다
  (`py ../quant-devtools/check_build_ready.py Quant/build_win`에 걸렸다 — configure 때 콘솔 인코딩이
  달라 `/showIncludes` 머리말 바이트가 안 맞은 것이다). 오브젝트 일부가 헤더 변경 뒤에도 다시
  컴파일되지 않았을 수 있다. 여기 수치는 그 상태로 잰 것이고, 다음 장중 재측정은
  그 빌드 폴더를 **지우고 다시 만든 뒤** 낸다(`--clean-first`로는 안 낫는다 — 머리말 바이트는
  configure 때 박힌다).

## 3. 결과 — 1초 주기

| 재는 것 | 값 |
|---|---|
| 한 바퀴 요청 수 | 4번 |
| 요청 / 실패 | 1,202 / **0** |
| 받은 종목 | 2,649 (요청 2,700 중) |
| 한 바퀴 소요 | 평균 **107ms** · 최대 1,454ms |
| 주기를 넘긴 바퀴 | 3 / 1,202 (0.25%) |
| 받은 양 | 1,254MB / 300초 = **4.2MB/s**(34Mbps) |
| 값이 바뀌어 흘린 건수 | 55,260 = 초당 **184건** |
| 신호 → 주문 | 245 → **240건** |
| 주문 전 구간 지연 | p50 **4.6ms** · p99 243ms · 최대 246ms |
| 큐 드롭 | 전 구간 0 |

**답은 된다.** 2,700종목 한 바퀴에 107ms, 주문 한 건이 게이트·라우터를 지나는 데 최악 246ms. 둘을 더해도
1초 예산의 절반이 안 된다.

받은 종목이 2,649인 것은 막혀서가 아니다. 유니버스에 상장폐지·거래정지 코드가 51개 섞여 있어 응답에 안 실린다.
매 바퀴 같은 51개가 빠지므로 유니버스 파일을 정리할 일이지 피드 문제가 아니다.

## 4. 결과 — 7초 주기와 견주면

응답 본문에 `pollingInterval: 7000`이 실려 온다. 웹페이지 자신이 7초에 한 번 다시 부르는 값이다. 같은 조건으로
7초 주기를 한 번 더 쟀다.

| | 1초 주기 | 7초 주기 | 배수 |
|---|---|---|---|
| 분당 요청 | 240 | 34 | 7.0× |
| 받은 양 | 4.2MB/s | 0.6MB/s | 7.0× |
| 한 바퀴 소요(평균) | 107ms | **433ms** | 0.25× |
| 한 바퀴 소요(최대) | 1,454ms | 10,345ms | 0.14× |
| 5분에 잡은 시세 변화 | 55,260 | 26,419 | 2.1× |
| 5분에 난 주문 | 240 | 153 | 1.6× |
| 주문 지연 p50 | 4.6ms | 15.2ms | 0.30× |

두 가지가 뒤집혀 있다.

**한 바퀴가 7초 주기에서 네 배 느리다.** 요청 사이가 7초면 keep-alive 연결이 식어 매번 TLS를 다시 맺는다.
1초 주기는 연결이 살아 있어 왕복만 든다. 부르는 쪽을 아끼려고 주기를 늘리면 **요청 하나하나는 더 무거워진다.**

**주기를 7배 늘려도 잃는 시세는 2.1배뿐이다.** 한 종목이 1초 안에 값이 바뀔 확률이 7%라서다 — 7초를 기다리면
그 종목이 바뀌었을 확률이 23%로 오르지, 일곱 배가 되지 않는다. 트래픽은 정직하게 1/7로 줄고 잡는 것은 절반만
준다. **트래픽당 정보로 보면 7초가 3.4배 낫다.**

## 5. 이 피드로 못 하는 것

**체결 하나하나가 필요한 전략은 못 한다.** 1초 스냅샷은 그 사이 체결 수십 건을 한 건으로 뭉친다. B회차에서
09-21 실제 캡처로 환산한 값은 2,700종목 초당 1,592건(중앙값)이었는데, 이 피드가 내는 것은 초당 184건이다.
**8분의 1이다.** 체결강도·호가 불균형·시장조성처럼 체결의 순서와 개수를 보는 전략은 이 입력으로 성립하지
않는다. 가격 경로만 있으면 되는 전략(돌파·추세·가치 기울임)은 된다.

**호가가 없다.** 이 엔드포인트는 현재가·누적거래량만 준다. 호가창을 보는 전략은 KIS 41종목에 묶인다.

**버스트가 주문 경로를 때린다.** 체결마다 주문을 내는 카운터 전략으로 같은 조건을 돌리면 지연 p50이 **404ms**,
p99 996ms까지 올랐다. 초당 평균은 185건인데 그것이 107ms 안에 몰려 들어와 순간 유량이 초당 1,700건 상당이 되고,
B회차에서 잰 주문 스레드 천장(초당 300~350건)에 걸린다. ITB는 5분에 240건뿐이라 이 벽을 안 만났다.
**주문을 많이 내는 전략을 이 피드에 붙이려면 주문 경로를 먼저 넓혀야 한다.**

## 6. 같이 고친 것

`Quant/src/api/KisTransport.cpp`의 `crack_url`이 URL 경로를 4096자 고정 버퍼로 받고 `WinHttpCrackUrl`의 실패
반환값을 보지 않았다. 675종목을 묶은 URL은 4,725자라 분해가 실패했고, **빈 경로로 요청이 나가 응답이 통째로
비었다** — 오류 한 줄 없이. 버퍼를 URL 길이로 잡고 실패를 반환하게 고쳤다. 지금 KIS 호출 중에 4096자를 넘는
것은 없지만, 종목을 많이 묶는 조회를 나중에 더하면 같은 자리에 다시 걸린다.

## 7. 쓸 것인가 — 지금은 재는 데까지만

이 주소는 공개 문서가 있는 API가 아니라 웹페이지 안에서 쓰는 것이다. 그래서 두 가지를 정해 두고 쓴다.

**받은 값은 밖으로 내보내지 않는다.** 매매 판단에만 들어간다. 연구 대시보드는 이미 바깥으로 발행되므로
(`research/dashboard/`) 이 피드 값을 거기 싣지 않는다. 부하 시험에 적는 것은 유량·지연 같은 집계값이지
종목별 가격이 아니다.

**이쪽이 실패하면 실매매가 같이 먼다.** `scripts/live_prices_feed.py`가 같은 주소를 같은 IP로 부른다 — 실매매 유니버스
스캔이다. 실패는 조용히 온다: HTTP 200에 본문이 비어 온다. 피드가 "200인데 종목 0건"을 실패로 세는 이유가 그것이다.

주기는 상수로 박지 않고 `--sweep-ms`로 뺐다. 상시 운영을 켠다면 7초 쪽이 트래픽당 정보가 3.4배 낫다. 1000과 7000 두 값은
그 차이를 보려고 고른 것이다.
