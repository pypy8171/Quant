# M회차 — 버린 2,300만 건은 전부 체결 링이고 소켓은 한 건도 안 버렸다 (2026-09-23)

측정한 코드: 엔진 **`6a629a6` + 이 회차의 `STATUS` 확장**(브랜치 `wt/auction`). D-126 계측 23열.

## 이전 회차 대비

J~L회차에서 "접수분의 상당수가 어디로 갔나"에 답하지 못했다. 원인별 카운터는 D-125 때 이미 넷으로 갈라 두었는데,
그 값이 `health` 표에 한 줄도 안 남아 있었기 때문이다. 이 회차는 그 값을 읽을 수 있게 만들고 읽었다.

| | J~L회차 | M회차 |
|---|---|---|
| 버린 건수 내역 | 못 읽음(`health` 0행) | 읽음 — 체결 링 100% |
| 읽는 통로 | 발행 큐(HEALTH) | 요청·응답(`STATUS`) |
| 적재기 붙였을 때 버린 건수 | — | 2,327만 건 |

## 1. 왜 못 읽었나 — 계측이 자기 자신을 잃는다

버린 건수는 `HEALTH` 메시지에 실려 나간다. 그런데 `HEALTH`는 주문·체결·신호와 같은 발행 큐를 타고,
그 큐에서 `HEALTH`는 **더 작은 한도**를 쓴다(`Quant/src/ipc/ZmqBridge.cpp`의 `enqueue`, D-125의 의도된 차등).
큐가 차면 원장에 직결되는 것부터 지키느라 `HEALTH`가 가장 먼저 버려진다.

그래서 **버리는 중일 때만 버린 건수가 사라진다.** J~L회차 구간(15:30~17:15)의 `health` 표 71행은 전부 마감 뒤 놀던
라이브 엔진 것이고, 부하 엔진 행은 0이었다. 엔진이 놀 때만 상태 보고가 도착한다는 것을 90초 구동으로 따로 확인했다.

고침은 읽는 통로를 바꾼 것이다. 요청·응답 소켓의 `STATUS` 명령은 발행 큐를 안 거치므로, 큐가 포화한 동안에도 답한다.
`Quant/src/core/Engine.cpp`의 `STATUS` 응답에 `drop`과 원인별 넷을 실었다.

## 2. 무엇을 돌렸나

```
창1  quant_trader.exe Quant\config\config_load_test.json     (부하 엔진, PUB 5555 / REP 5556)
창2  PYQuant\main.py record --port 5555 --record-ticks --account 00000000   (적재기, 붙인 회차만)
창3  python -m tools.load_injector --orders-per-symbol 30000 --seed 20260923 (2,700종목)
     10초마다 REP 5556 에 STATUS
```

난수 시드가 같아 투입은 J회차와 같은 입력이다. 적재기 없는 쪽에도 주문·체결·신호만 받는 구독자가 붙어 있었다
(틱은 안 받는다) — 구독자가 없어서 버린 것이 아님을 뜻한다.

## 3. 버린 것은 전부 체결 링이다

| | 적재기 없음 | 적재기 붙임 |
|---|---|---|
| 들어온 시세 건수 | 54,507,632 | 54,507,632 |
| 투입 시간 | 80.2초 | 80.3초 |
| 초당 | 679,647건 | 678,800건 |
| **버린 것 합계** | **18,457,068** | **23,275,143** |
| 소켓이 안 받음 | 0 | 0 |
| 보내다 예외 | 0 | 0 |
| 발행 큐 만석 | 0 | 0 |
| **체결 링 만석** | **18,457,068** | **23,275,143** |

네 갈래 중 **체결 링 하나가 100%**다. 소켓 쪽은 한 건도 없다. 즉 병목은 내보내는 소켓이 아니라 그 앞의 링이고,
링을 키우거나 빼내는 쪽을 빠르게 하는 것이 유일한 손잡이다. 시세는 54,507,632건 중 33.9%(적재기 붙이면 42.7%)가
링에서 버려졌다.

적재기를 붙이면 버린 것이 1,846만 → 2,328만으로 **26% 늘고**, 같은 시간에 엔진이 처리한 주문은
14,646 → 11,059건으로 **24% 줄었다**. J~L회차에서 잰 "적재기를 붙이면 주문 경로가 1.5~1.7배 느려진다"와 같은 방향이다.

## 4. 주문은 엔진이 안 버렸다 — 구멍은 그 뒤에 있다

주문·체결·신호는 발행 큐를 타는데 그 큐의 만석 카운터가 **0**이다. 엔진은 주문을 한 건도 안 버렸다.
그런데 DB에 남은 주문은 11,059건 중 6,253건(56.5%)뿐이다.

| | 엔진이 처리 | DB에 남음 | 비율 |
|---|---|---|---|
| 주문 | 11,059 | 6,253 | 56.5% |
| 신호 | 99,522 | 5,178 | 5.2% |
| 체결 | — | 1,245 | — |
| 시세 | 54,507,632 | 22,814 | 0.04% |

빠진 4,806건은 엔진 밖에서 사라졌다 — 받는 쪽 소켓 상한이거나, 파이썬 적재기가 미처 못 넣고 끝난 몫이다.
이 회차의 계측으로는 둘을 못 가른다. J~L회차에서 본 "22~31%만 DB에 닿는다"의 나머지도 여기에 있다.

## 5. 기계가 먼저 무너진다

투입 10초 시점의 가용 메모리가 **0.29GB**까지 내려갔다. 앞선 회차에서는 이 압박으로 **WSL이 내려갔고,
그 안의 TimescaleDB가 같이 죽어** 측정이 한 번 끊겼다. 부하 회차는 DB 호스트를 같이 태운다는 뜻이라,
다음부터는 가용 메모리를 회차 기록에 같이 남긴다.

## 6. 한계

- 적재기 없는 쪽에도 주문·체결·신호 구독자가 붙어 있었다. 완전한 무구독 대조가 아니다.
- 적재기는 투입 종료 20초 뒤에 껐다. 그때까지 못 넣은 몫은 "빠진 것"으로 잡혔다.
- 엔진·적재기·DB가 한 기계에 있다. 분리하면 숫자가 달라진다.
- 한 회차씩만 쟀다. 회차 간 편차는 모른다.
